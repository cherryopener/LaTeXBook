# 교재 편집기 구축 계획 (서브에이전트 배분안)

워드처럼 편하게 쓰고, 수식은 LaTeX(KaTeX)로 곱게 나오며, 인쇄용 PDF까지 뽑는 웹 편집기를 만드는 계획입니다.

- 작성: 2026-11-07
- 상태: **계획 검토 중**. 아직 코드를 쓰지 않았습니다. 9절의 질문에 답을 받은 뒤 0단계를 시작합니다.
- 참고한 것: `cherryopener/cherryopener.github.io`의 `CLAUDE.md`(모델 배정 규칙 4절, 병렬 작업 절차 5절), `templates/chapter.html`(KaTeX 0.16.9 사용 방식)

---

## 1. 결론 요약

1. **화면 구성**: 왼쪽은 원고(마크다운 + `$수식$`), 오른쪽은 **실제 인쇄될 페이지 모양** 미리보기입니다. 입력하면 0.3초 뒤 오른쪽이 다시 그려집니다.
2. **페이지 나누기 엔진은 Vivliostyle**을 씁니다. 처음 떠올리기 쉬운 Paged.js는 2023-07(0.4.3) 이후 새 버전이 확인되지 않아 제외합니다. Vivliostyle은 2026-09에도 새 버전(v2.45.1)이 나왔고, 일본어 조판에서 출발해 한·중·일 글자 처리가 강합니다.
3. **PDF는 두 갈래**입니다.
   - 일반 PDF: 브라우저의 "PDF로 저장"으로 바로 뽑습니다. 별도 서버가 없습니다.
   - 인쇄소 제출용 PDF(CMYK, PDF/X-1a): 브라우저만으로는 만들 수 없습니다. Vivliostyle CLI의 `press-ready` 기능을 GitHub Actions에서 돌리는 방식으로 나중 단계에 붙입니다. 인쇄 방식에 따라 필요 없을 수도 있습니다(9절 질문 2).
4. **서브에이전트는 총 6개 역할, 동시 최대 4개**로 돌립니다. 모든 에이전트가 따를 "원고 형식 명세"와 "모듈 사이 약속(함수 모양)"은 메인 세션이 먼저 확정합니다. 이것이 흔들리면 병렬 작업이 전부 흔들립니다.

## 3. 기술 선택

| 영역 | 선택 | 이유 | 0단계에서 확인할 것 |
|---|---|---|---|
| 원고 형식 | 마크다운 + 확장 문법 | 사이트에서 쓰던 `\( \)`, `$ $` 수식을 그대로 씀 | — |
| 변환 | markdown-it + KaTeX 0.16.x | 사이트와 같은 KaTeX, 플러그인으로 상자·2단·그림 블록 추가 | — |
| 편집 화면 | CodeMirror 6 | 수식 자동 완성, 괄호 짝 맞춤, 대용량 원고에도 빠름 | CDN(ESM)만으로 빌드 없이 돌아가는지 |
| 페이지 나누기 | Vivliostyle.js | 머리말·꼬리말, 쪽 번호, 좌우 페이지, 도련·재단선 지원 | 브라우저에 삽입하는 방법, 2단이 페이지를 넘어갈 때 |
| 함수 그래프 | function-plot 또는 JSXGraph | 원고에 식을 적으면 그래프가 그려짐 | 질문 3의 답에 따라 결정 |
| 데이터 차트 | Vega-Lite | 원고에 표 데이터를 적으면 차트가 됨, SVG로 인쇄 품질 유지 | 질문 3의 답에 따라 결정 |
| 한글 글꼴 | 본문 Noto Serif KR(본명조), 제목 Pretendard 또는 Noto Sans KR | 둘 다 OFL 라이선스라 PDF 포함·배포 가능 | PDF에 글꼴이 포함되는지(`pdffonts`) |
| 저장 | 브라우저 내부(IndexedDB) 자동 저장 + 파일 내보내기/불러오기 | 서버 없이 GitHub Pages에서 동작 | 질문 4의 답에 따라 GitHub 저장 추가 |
| 배포 | GitHub Pages | 기존 사이트와 같은 방식 | 저장소 공개 여부 |

- **빌드 도구 원칙**: 기존 사이트처럼 "빌드 없이 CDN, 버전 고정"을 기본으로 합니다. 0단계에서 CodeMirror 6이나 Vivliostyle이 CDN만으로 안 되면, 그때 Vite 빌드 + GitHub Actions 배포로 바꿀지 사용자에게 묻습니다.

## 4. 인쇄·제본 기본값 (책 조판 관례)

일반적인 웹 문서와 다른, 책 조판의 관례를 기본값으로 넣습니다.

- **용지**
  - A4: 210×297mm
  - **216×303mm는 A4에 사방 3mm 재단 여유(도련)를 더한 크기**입니다(210+3+3, 297+3+3). 인쇄소에서 A4 책의 "작업 사이즈"로 흔히 요구하는 값입니다. 그래서 별도 용지가 아니라 **"A4 완성 + 도련 3mm" 출력 옵션**으로 만드는 것을 제안합니다. 배경색·그림이 종이 끝까지 닿는 페이지가 깔끔하게 잘립니다. (추정이므로 질문 2로 확인합니다)
  - 재단선(재단 위치 표시) 표시 여부는 선택 옵션으로 둡니다. 인쇄소마다 요구가 다릅니다.
- **좌우 페이지**: 제본하면 왼쪽·오른쪽 페이지가 마주 보므로, 안쪽 여백(제본 쪽)을 바깥보다 넓게 하고 좌우 페이지 여백을 거울처럼 뒤집습니다.
- **쪽 번호**: 꼬리말의 바깥쪽(왼쪽 페이지는 왼쪽, 오른쪽 페이지는 오른쪽)에 둡니다. 가운데 정렬도 옵션으로 둡니다.
- **머리말**: 장 제목이 자동으로 들어갑니다. 장이 시작하는 첫 페이지에는 머리말을 숨깁니다. 로고·그림 장식은 사용자가 보낼 PDF 예시를 받은 뒤 "디자인 테마"로 만듭니다(6단계).
- **장 시작**: 새 장은 오른쪽 페이지에서 시작하는 옵션을 둡니다(필요하면 앞에 빈 페이지 자동 삽입).
- **한글 줄바꿈**: 단어 중간에서 줄이 바뀌지 않게 합니다(`word-break: keep-all`). 수식이 줄 끝에서 잘리지 않게 합니다.
- **2단**: 문서 전체 2단, 또는 특정 구간만 2단(`::: columns` 블록). 제목·큰 그림은 두 단을 가로질러 놓을 수 있게 합니다.

## 6. 단계와 서브에이전트 배분

모델·effort 단계는 기존 사이트 `CLAUDE.md` 4-2절의 사다리를 그대로 씁니다. 같은 문서 4-5절의 "엔진·레이아웃 수정 2단계, 여러 파일에 걸친 구조 변경 4단계" 규칙을 적용했습니다.

| 단계 | model / effort |
|---|---|
| 0 | haiku / low |
| 1 | sonnet / medium |
| 2 | sonnet / high |
| 3 | opus / medium |
| 4 | opus / high |
| 5 | opus / xhigh |

### 0단계. 기술 검증 (메인 세션 직접, 서브에이전트 없음)

가장 불확실한 부분을 먼저 작은 시험 페이지 하나로 확인합니다. 여기서 막히면 계획을 고칩니다.

- [ ] Vivliostyle을 브라우저 페이지에 넣고, KaTeX로 그린 수식이 페이지 사이에서 깨지지 않는지
- [ ] 머리말에 장 제목, 꼬리말에 쪽 번호가 들어가는지(좌우 페이지 구분 포함)
- [ ] 2단 구간이 페이지를 넘어갈 때 제대로 이어지는지 — **페이지 나누기 엔진들의 알려진 약점**이라 가장 먼저 봅니다
- [ ] A4, A4+도련(216×303) PDF가 정확한 크기로 나오는지(`pdfinfo`로 mm 확인)
- [ ] 한글 글꼴이 PDF 안에 포함되는지(`pdffonts`)
- [ ] CodeMirror 6, Vivliostyle이 CDN만으로 동작하는지
- 산출물: `spike/` 시험 페이지, `docs/DECISIONS.md`(채택·포기한 것과 이유)
- **사용자 확인 지점 ①**: 시험 PDF 2개(A4, 216×303)를 보여 드리고 넘어갑니다.

### 1단계. 뼈대와 약속 정하기 (메인 세션 직접)

- [ ] `docs/FORMAT.md`: 원고 형식 명세(5절 확정본)
- [ ] `docs/INTERFACES.md`: 모듈 사이 함수 모양
  - `render(markdown) → { html, meta }` (meta: 장 목록, 그림·식 번호표)
  - `paginate(html, settings) → 페이지 미리보기`
  - `settings`: 용지, 단 수, 여백, 글꼴, 머리말·꼬리말 구성
- [ ] 폴더 구조와 빈 파일, 견본 원고 `samples/sample-chapter.md`(모든 기능을 한 번씩 쓰는 1장 분량)
- 견본 원고가 이후 모든 단계의 **합격 시험지**입니다.

### 2단계. 병렬 개발 (서브에이전트 4개 동시)

각 에이전트는 **자기 폴더만** 고칩니다. 다른 폴더에 바꿀 것이 필요하면 보고서에 제안으로만 적습니다. 서로 겹치지 않게 각자 별도 작업 사본(git worktree)에서 일합니다.

| 역할 | 맡는 폴더 | 할 일 | 단계 (model/effort) | 이유 |
|---|---|---|---|---|
| A. 편집 화면 | `src/editor/` | CodeMirror 화면, 워드식 도구 막대(굵게·표 삽입·수식 삽입·그림 삽입 버튼), 수식 자동 완성, 원고↔미리보기 스크롤 맞춤 | 2 · sonnet/high | 일반적인 UI 작업 |
| B. 원고 변환 | `src/render/` | markdown-it + KaTeX, 상자·2단·그림·페이지 나눔 문법, 식·그림 자동 번호와 상호 참조 | 3 · opus/medium | 모든 출력의 기준이라 틀리면 전체가 틀림 |
| C. 조판·인쇄 | `src/layout/`, `themes/` | Vivliostyle 연결, 인쇄용 CSS(용지·도련·좌우 여백·머리말·꼬리말·장 시작·2단·한글 줄바꿈), 글꼴 | 4 · opus/high | 가장 어렵고, 여러 규칙이 서로 얽힘 |
| D. 그림·표·그래프 | `src/figures/` | 그림 끌어다 놓기, 표 편집 도우미, 함수 그래프·데이터 차트 블록 | 2 · sonnet/high | 범위는 넓지만 각 기능은 표준적 |

- A와 B는 1단계의 약속(`render` 함수 모양)만 맞추면 서로 기다리지 않습니다.
- C는 B의 결과물 대신 **손으로 쓴 견본 HTML**로 먼저 작업하고, 3단계에서 연결합니다.

### 3단계. 저장 기능 + 통합 (서브에이전트 1개 + 메인 세션)

| 역할 | 맡는 폴더 | 할 일 | 단계 |
|---|---|---|---|
| E. 저장·불러오기 | `src/storage/` | 브라우저 자동 저장, 프로젝트(원고+그림) 파일 내보내기/불러오기, 질문 4 답에 따라 GitHub 저장 | 2 · sonnet/high |

- 메인 세션이 A~E를 하나로 합치고, 견본 원고로 끝까지(입력 → 미리보기 → PDF) 돌려 봅니다.
- **사용자 확인 지점 ②**: 실제로 써 보시고, 불편한 점을 받습니다.

### 4단계. 검토 (서브에이전트 2개, 고치지 않고 지적만)

기존 규칙대로 **검토는 작성보다 한 단계 위**가 맡습니다.

| 역할 | 대상 | 단계 |
|---|---|---|
| F1. 코드 검토 | A·B·D·E | 4 · opus/high (가장 높은 작성 단계 3보다 위) |
| F2. 조판 검토 | C + 실제 PDF 페이지 | 5 · opus/xhigh (작성 단계 4보다 위) |

- F2는 견본 원고로 PDF를 뽑아 페이지마다 화면 사진을 찍고, 머리말·쪽 번호·여백·줄바꿈·수식 잘림을 하나씩 점검합니다.
- 지적 사항은 메인 세션이 반영하거나, 그 부분을 만든 에이전트에게 이어서 보내 고치게 합니다.

### 5단계. 배포

- [ ] GitHub Pages에 올리고 주소를 드립니다.
- [ ] 사용 설명서(`README.md`, 한글)

### 6단계. 디자인 테마 (사용자가 PDF 예시를 보낸 뒤)

- [ ] 보내 주신 예시에 맞춰 머리말 로고, 장 시작 페이지 그림 장식을 테마로 만듭니다.
- 담당: C 역할을 이어서(4 · opus/high). 1단계에서 머리말을 "글자+그림 자리"로 설계해 두므로 큰 공사 없이 붙습니다.

### 7단계. 인쇄소용 PDF (필요한 경우만)

- [ ] GitHub Actions에서 Vivliostyle CLI `press-ready`로 PDF/X-1a를 만드는 작업 흐름
- 담당: 2 · sonnet/high
- 질문 2의 답이 "디지털·소량 인쇄"이면 생략할 수 있습니다.

### 전체 규모

- 서브에이전트 호출: 약 7~9회(수정 재요청 포함 시 10회 남짓). 추정치입니다.
- 사용자 확인 지점: 0단계 끝, 3단계 끝, 6단계(예시 PDF 전달) 세 번입니다.

## 7. 서브에이전트에게 넘길 내용 (공통)

서브에이전트는 이 대화를 모르므로, 매번 아래를 모두 넣습니다.

- 목표와 맡은 역할, 맡은 폴더(이 폴더만 수정 가능)
- `docs/FORMAT.md`, `docs/INTERFACES.md`, `docs/DECISIONS.md` 경로
- 견본 원고 경로와 합격 기준(견본 원고가 오류 없이 처리될 것)
- 버전 고정 규칙(CDN 주소에 정확한 버전)
- 화면에 보이는 글자는 한국어
- 보고 형식: ① 만든 것 ② 약속(INTERFACES)과 다르게 한 곳 ③ 확인한 것과 못 한 것 ④ 다른 폴더에 대한 변경 제안
- `Agent` 호출 때 `model`과 `effort`를 6절 표대로 반드시 지정합니다.

## 8. 위험과 대책

| 위험 | 영향 | 대책 |
|---|---|---|
| 특정 구간만 2단이 페이지를 넘어갈 때 엔진이 제대로 못 나눔 | 2단 기능 일부 제한 | 0단계에서 먼저 확인. 안 되면 "2단은 문서·장 단위로만" 같은 제약을 사용자와 정함 |
| 원고가 길어지면(100쪽 이상) 실시간 미리보기가 느려짐 | 입력이 버벅임 | 미리보기는 지금 쓰는 장만 다시 그림. 전체 페이지는 PDF 뽑을 때만 계산 |
| 브라우저 PDF는 RGB 색 | 옵셋 인쇄소에서 색이 달라지거나 거절 | 7단계(press-ready, CMYK 변환). 인쇄소 요구 사항을 미리 받아 두면 좋음 |
| 상용 한글 글꼴을 쓰고 싶을 때 | 라이선스상 공개 저장소에 글꼴 파일을 올릴 수 없음 | 기본은 OFL 글꼴. 상용 글꼴은 사용자 컴퓨터에서만 불러오는 방식 |
| "워드처럼 페이지 위에서 바로 편집"은 웹에서 매우 어려움 | 처음 기대와 다를 수 있음 | 분할 화면 + 도구 막대로 편의를 채우는 쪽을 권장(질문 1) |

## 9. 시작 전에 정할 것

1. **편집 방식**: 왼쪽 원고 / 오른쪽 페이지 미리보기 분할(권장), 또는 워드처럼 페이지 위에서 바로 편집(개발 기간이 크게 늘고 안정성이 떨어짐)
2. **216×303의 뜻과 인쇄 방식**: A4 완성본에 도련 3mm를 더한 인쇄소 작업 크기가 맞는지. 그리고 옵셋 인쇄소(CMYK 요구 가능)인지, 디지털·소량 인쇄(보통 일반 PDF로 충분)인지
3. **그래프 종류**: 함수 그래프(식으로 그림) / 데이터 차트(막대·꺾은선) / 둘 다 / 그림 파일만
4. **원고 저장 위치**: 브라우저 + 파일 내보내기(가장 간단) / GitHub 저장소에도 저장(여러 컴퓨터에서 이어 쓰기)
5. **기존 사이트와의 연결**: 이 편집기로 쓴 원고를 지식따개 사이트의 장으로도 내보낼지(그렇다면 상자·번호 규칙을 사이트와 똑같이 맞춤)
